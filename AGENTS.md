# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`smg-live-alter` is a single-binary Go CLI for applying MySQL `ALTER TABLE` statements without downtime. It is an alternative to `pt-online-schema-change` (Percona) and `gh-ost` (GitHub) — see `README.md` for the rationale (mainly: trigger preservation, simplicity, correct handling of binary columns).

The tool is published as a Go module: `github.com/StirlingMarketingGroup/smg-live-alter/v2` (the `/v2` suffix matters — the module path includes it).

## Common commands

```sh
go build ./...                                # compile
go vet ./...                                  # static checks
go test ./...                                 # unit tests; they do not need a database
go install github.com/StirlingMarketingGroup/smg-live-alter/v2@latest   # install from upstream
go run . 'user:pass@(host)/dbname'            # run from source against a DSN
go run . localhost                            # run using a named connection from connections.yaml
```

The unit tests cover the lexicographic key predicates (`keyrange.go`), identifier quoting, the column mapping, unique-index coverage (including value-keeping conversions), the destination key and its conversions (`model.go`), the primary-key type check, check-name rewriting, constraint splitting, inbound foreign-key requirements, the restore plan and recovery SQL, and the cascading foreign-key rule. An alter against a real server is not covered by `go test`.

The connections file lives at `os.UserConfigDir()/smgla/connections.yaml` (e.g. `~/Library/Application Support/smgla/connections.yaml` on macOS, `~/.config/smgla/connections.yaml` on Linux). See `connections-example.yaml`.

The alter statement itself is collected interactively by opening `nano` on a temp file (`prompt.go`), not via flags or stdin. There is no non-interactive mode.

## How the live alter works (read this before changing core logic)

The flow in `main.go` is sequential and the ordering matters. Broadly:

1. **Build the temp table.** Run `SHOW CREATE TABLE`. `splitConstraints` (`constraints.go`) classifies each CONSTRAINT line by the token after the name (`FOREIGN KEY` or `CHECK`; anything else is an error). Foreign keys come out as a slice — FK names are globally unique in MySQL, so the temp table can't reuse them; they are re-added after the original table is dropped — and check constraints stay in the statement: a generated name `<table>_chk_<n>` becomes `<temp>_chk_<n>`, which MySQL renames back to `<table>_chk_<n>` with the table, and a custom name is dropped so MySQL generates one. `rewriteCheckNames` rewrites the constraint-name operand of `DROP CHECK`, `ALTER CHECK`, `DROP CONSTRAINT`, and `ALTER CONSTRAINT` in the user's alter from `<table>_chk_<n>` to `<temp>_chk_<n>` before that alter runs, only in text outside string literals and comments. Create `<table>_smgla_` from the modified DDL, then apply the rewritten alter to it. Before any of that, the source primary key is loaded in `Seq_in_index` order and checked: every key column's `DATA_TYPE` must be one of `tinyint`, `smallint`, `mediumint`, `int`, `bigint`, `decimal`, `binary`, `varbinary`, `char`, `varchar`. The copy cursor lives in user variables, and other types don't compare like the index. A foreign key on the source whose `UPDATE_RULE` or `DELETE_RULE` is `CASCADE`, `SET NULL`, or `SET DEFAULT` is refused: MySQL changes those rows without firing triggers, so the temp table can't follow them. A foreign key whose referenced table is the source itself is refused: the probe would resolve it against the old schema. One `database/sql` connection is pinned right after the source columns are read, so those lookups bind table names with `?`.
2. **Decide whether the alter can be mirrored.** `getTableColumns` (`columns.go`) pulls column metadata, including `COLLATION_NAME` and `CHARACTER_SET_NAME`, from `information_schema.columns`, plus primary-key order from `SHOW INDEX`. `getUniqueIndexes` loads every unique index (`Non_unique=0`), parts in `Seq_in_index` order. `buildColumnMapping` (`model.go`) walks the source columns in source order, applies `CHANGE COLUMN` renames from `parseChangeColumnRegex`, and keeps each pair whose destination exists on the temp table and is not generated. A generated source column whose destination exists and is stored is an error: triggers cannot read generated columns. Source generated with a generated destination, or a missing destination, is skipped. That one list is the copy's insert list and select list, and the column list the three triggers write, so an `AFTER` or `FIRST` reorder can't mis-pair them. Unique coverage also counts a derived column: a generated column whose expression is a conditional projection (`` `col` ``, or `if(<cond>, `col`, NULL)` / `if(<cond>, NULL, `col`)`) of a copied column, with the generated type equal to the projected column's type on each side, and a condition that is one integer column compared with an integer literal, unchanged by the alter. Any other generated column in a destination unique index has to be covered without that proof. `checkUniqueCoverage` requires, for every destination unique index, a source unique index whose every part maps to one of the destination's parts, so extra destination parts need no proof. Copied columns and derived columns both count. A functional source index covers nothing. Parts compare on column name and prefix length exactly. A collation change on a destination unique column that is copied or derived is refused. `keyConversionKeepsValues` refuses a conversion that does not keep values on a mapped unique column, for every unique index, the primary key included, because two distinct source rows could land on one destination key. `destinationKey` requires a destination primary key. It is that key in destination key order, each column paired with the source column copied into it. A destination key column that is not a mapping destination is an error. The storage engine of the source and temp tables must match. Inbound foreign keys (other tables that reference this one) re-attach by name after the rename, so every referenced column must map to a destination column with the same name, identical `COLUMN_TYPE`, and identical character set and collation, and the destination must have an index whose leading parts are exactly those columns in that order with no prefix length. After `destinationKey`, and before any mirror trigger exists, `readRestorePlan` builds one restore plan and `validate` compiles it against a probe table (`<table><suffix>probe_`) created `LIKE` the temp table. The probe proves the foreign key definitions and the original trigger bodies compile against the altered columns. It does not prove the rename, permissions, or anything another session changes. Either check failing stops the run before any trigger is created; the temp table is left for the next run to drop.
3. **Install three triggers** on the source table (`*_after_delete_smgla_`, then `*_after_update_smgla_`, then `*_after_insert_smgla_`) that mirror writes into the one temp table. They are created on the pinned connection after `set session sql_mode=@@global.sql_mode`, because a trigger keeps the sql_mode it was created with and the application's sessions use the server's global mode. None of them uses `IGNORE`. The delete trigger deletes the temp row whose destination key equals the old source key. The update trigger updates that temp row in place (so a primary-key change moves it and destination-only columns stay), then inserts the new row only when no temp row has the new key. The insert trigger inserts the new row. A write the destination rejects fails the application's statement.
4. **Bulk-copy rows in primary-key chunks, inside the server, on that same connection.** It runs `insert into <temp> (...) select ... from <source> where <range> lock in share mode on duplicate key update <first column>=<first column>`. A duplicate is the row a trigger already wrote, which unique coverage makes the only kind, and the no-op keeps it without a warning. The range is lexicographic on the source traversal key (the full source primary key in index order), compared against session variables `@smgla_k*` (the cursor) and `@smgla_e*` (this chunk's end key). The end key is the chunk-th key after the cursor: `order by <pk> limit 1 offset chunk-1`. Key values are never read into Go. `lock in share mode` holds the copied range until the statement ends.
5. **Adaptive chunk sizing.** Each copy statement is timed against a 500ms target. Over target, the chunk shrinks proportionally (`chunk * target / elapsed`, minimum 1). Under target, it grows by a tenth of the gap, and it does not grow past 10000 rows. Any warning from a copy statement stops the tool (`failOnCopyWarnings`, `copywarnings.go`). That rule is stricter than the triggers because the copy governs rows that already exist: a row that breaks a check constraint, or a value the alter narrows, must not be skipped or changed without an error. `-r` is the starting chunk size (default 1000, 1 to 10000).
6. **Drop / swap / restore, still on that connection.** After a `do the drop/swap?` y/n confirmation the plan is read again (fresh `SHOW CREATE TABLE` → `splitConstraints`, fresh trigger read, fresh inbound keys). If it is not `equal` to the validated plan, the run stops before the drop: the source's triggers or foreign keys changed during the copy; rerun the tool. That re-check is a cheap guard for the assumption that no other DDL ran on the table or its foreign key neighbors, not a proof. The plan's `steps` (the combined FK `ALTER TABLE`, each original trigger's `sql_mode`/`collation_connection` then `CREATE`, the session restore, then the rename) are written to `smgla-recovery-<table>-<unix seconds>.sql` in the working directory. A write failure stops before the drop. Then `set foreign_key_checks=0`, drop the original table, sleep 1s, and execute those same steps in order. Each success logs `done: <Purpose>`. A failing step names the step, MySQL's error, that `<table>` is dropped and its rows are in `<temp>`, and that the remaining steps in the recovery file finish the swap. `retargetTrigger` (`triggers.go`) rewrites both the trigger name and the table in the `TRIGGER … ON … FOR EACH ROW` header MySQL stores. `character_set_client` stays the connection's own, because the statement text comes back in that character set; the recovery file starts with `use <database>;` and `set names <charset>;` from `@@character_set_client` read before the drop.

The drop happens *before* the rename specifically to avoid a window where both tables exist with conflicting state — the README spells this out. There is intentionally a brief window where the table name does not resolve; callers must retry. Atomic `RENAME ... TO` is *not* used because it would also retarget FKs in other tables to the renamed table, and we want those FKs to land on the new schema.

Run the drop, constraint restoration, trigger restoration, and rename statements without a transaction.

### Primary key

`destinationKey` pairs each destination primary-key column, in destination `Seq_in_index` order, with the source column the mapping copies into it. The delete trigger matches the old source key. The update trigger matches the old source key, writes the new values in place, and inserts when the new key is absent. Unique coverage is what makes that key identify one source row, including when the primary key grows, shrinks, or is renamed.

## Code map

- `main.go` — full orchestration (steps above). Most logic still lives here; resist the urge to split it just for tidiness.
- `columns.go` — `information_schema` queries; primary-key detection, `Seq_in_index`, `COLLATION_NAME`, `CHARACTER_SET_NAME`, and indexes from `SHOW INDEX`. Also handles older MySQL versions that lack `GENERATION_EXPRESSION` (probes `information_schema` for the column itself before selecting it).
- `model.go` — the column mapping, unique-index coverage, the destination key and which key conversions keep values, the source traversal key, and the check that every traversal-key type can live in a user variable.
- `keyrange.go` — identifier quoting (`quoteIdent`, `quoteString`) and lexicographic `after` and `atOrBefore` predicates over the session-variable cursor.
- `constraints.go` — splits foreign keys out of `SHOW CREATE TABLE` by the token after the constraint name, gives generated check constraints temp names, and rewrites those names in the user's alter outside literals and comments. `referentialActionSkipsTriggers` is the cascading-action rule.
- `restore.go` — the restore plan, probe validation, recovery SQL, inbound foreign keys, and the post-drop step helper.
- `regexp.go` — two regexes: parse the user's alter into `(schema, table, alter-body)`, and find `CHANGE COLUMN` renames.
- `triggers.go` — rewrites the trigger name and table in the `TRIGGER … ON … FOR EACH ROW` header of `CREATE TRIGGER`, and reads `SHOW CREATE TRIGGER` for the statement text.
- `prompt.go` — `nano`-based alter input, `Y/n` confirmation reader.
- `connections.go` — YAML config loader and DSN builder (uses `go-sql-driver/mysql`'s `NewConfig` then appends URL-escaped extra params).

## Conventions

- Error handling is `panic`-on-error for setup failures in `main.go`. This is intentional: every setup panic happens before any mirror trigger exists, so the next run starts clean, and a panic is the clearest signal. Don't convert these to silent error returns. Refusals and the mirror session use `log.Fatalf`: the traversal-key type check, cascading and self-referential foreign keys, unique coverage, the destination key, inbound keys, the column mapping, probe validation, and every statement on the connection from the lookups through the swap. The message names what failed. After the drop, a failing restore step also names the recovery file.
- SQL identifiers go through `quoteIdent` (backticks, doubled internally). String literals in restore SQL go through `quoteString`. Table names come from the user's alter statement (parsed by regex), not from arbitrary input — but be careful adding new code paths that would interpolate untrusted strings into DDL.
- One `database/sql` connection (`db.Reads.Conn`; `db.Writes` has no `Conn`, and both pools use the same DSN) is pinned after the source columns are read and held through the swap, with `?` placeholders for lookups that bind table names as values. It does not go through cool-mysql interpolation, so `sql_mode`, `foreign_key_checks`, the copy's isolation level, and the `@smgla_*` cursor stay on that session. Statements before that connection still go through cool-mysql. Its placeholders are `@@name` (compile-time interpolated, often as `mysql.Raw`) and `@name` (parameter-bound).
