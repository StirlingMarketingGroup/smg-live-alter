# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`smg-live-alter` is a single-binary Go CLI for applying MySQL `ALTER TABLE` statements without downtime. It is an alternative to `pt-online-schema-change` (Percona) and `gh-ost` (GitHub) — see `README.md` for the rationale (mainly: trigger preservation, simplicity, correct handling of binary columns).

The tool is published as a Go module: `github.com/StirlingMarketingGroup/smg-live-alter/v2` (the `/v2` suffix matters — the module path includes it).

## Common commands

```sh
go build ./...                                # compile
go vet ./...                                  # static checks
go test ./...                                 # unit tests; they do not need a database
go install github.com/StirlingMarketingGroup/smg-live-alter/v2@latest   # install from upstream
go run . 'user:pass@(host)/dbname'            # run from source against a DSN
go run . localhost                            # run using a named connection from connections.yaml
```

The unit tests cover the lexicographic key predicates (`keyrange.go`), identifier quoting, the column mapping, unique-index coverage (including value-keeping conversions), the destination key and its conversions (`model.go`), the primary-key type check, check-name rewriting, constraint splitting, inbound foreign-key requirements, the restore plan and recovery SQL, the cut-over strategy, the cascading foreign-key rule, replica-lag pacing (`pacing.go`), `normalizeCreate`, the run-table DDL, and the resume decision (`run.go`). An alter against a real server is not covered by `go test`.

The connections file lives at `os.UserConfigDir()/smgla/connections.yaml` (e.g. `~/Library/Application Support/smgla/connections.yaml` on macOS, `~/.config/smgla/connections.yaml` on Linux). See `connections-example.yaml`.

The alter statement itself is collected interactively by opening `nano` on a temp file (`prompt.go`), not via flags or stdin. There is no non-interactive mode.

## How the live alter works (read this before changing core logic)

The flow in `main.go` is sequential and the ordering matters. Broadly:

1. **Build the temp table.** Run `SHOW CREATE TABLE`. `splitConstraints` (`constraints.go`) classifies each CONSTRAINT line by the token after the name (`FOREIGN KEY` or `CHECK`; anything else is an error). Foreign keys come out as a slice — FK names are globally unique in MySQL, so the temp table can't reuse them; they are re-added after the original table is dropped — and check constraints stay in the statement: a generated name `<table>_chk_<n>` becomes `<temp>_chk_<n>`, which MySQL renames back to `<table>_chk_<n>` with the table, and a custom name is dropped so MySQL generates one. `rewriteCheckNames` rewrites the constraint-name operand of `DROP CHECK`, `ALTER CHECK`, `DROP CONSTRAINT`, and `ALTER CONSTRAINT` in the user's alter from `<table>_chk_<n>` to `<temp>_chk_<n>` before that alter runs, only in text outside string literals and comments. Create `<table>_smgla_` from the modified DDL, then apply the rewritten alter to it. Before any of that, the source primary key is loaded in `Seq_in_index` order and checked: every key column's `DATA_TYPE` must be one of `tinyint`, `smallint`, `mediumint`, `int`, `bigint`, `decimal`, `binary`, `varbinary`, `char`, `varchar`. The copy cursor lives in user variables, and other types don't compare like the index. A foreign key on the source whose `UPDATE_RULE` or `DELETE_RULE` is `CASCADE`, `SET NULL`, or `SET DEFAULT` is refused: MySQL changes those rows without firing triggers, so the temp table can't follow them. A foreign key whose referenced table is the source itself is refused: the probe would resolve it against the old schema. One `database/sql` connection is pinned right after the source columns are read, so those lookups bind table names with `?`. The source engine has to be InnoDB, because each copied chunk and its checkpoint commit in one transaction. Before that cleanup, a run resumes when `-fresh` is not set and the run table `<table><suffix>run_` exists, has its row, and that row's alter text is this alter. A run table for a different alter starts fresh. `-fresh` discards a stopped run of this alter and copies from the first row. A fresh run's cleanup drops the mirror triggers, then the run table, then the temp table. A resumed run drops only the probe table and keeps the temp table, the triggers, and the run record. After `set session sql_mode=@@global.sql_mode`, and before any mirror trigger exists, a fresh run creates that run table once (explicit `engine=InnoDB`, one row): the alter text, the normalized source and temp `SHOW CREATE TABLE` output read after that sql_mode set, one nullable cursor column per traversal-key column, `copy_done`, and the Aurora readers seen so far. `normalizeCreate` strips the table `AUTO_INCREMENT` option, which moves on every insert.
2. **Decide whether the alter can be mirrored.** `getTableColumns` (`columns.go`) pulls column metadata, including `COLLATION_NAME` and `CHARACTER_SET_NAME`, from `information_schema.columns`, plus primary-key order from `SHOW INDEX`. `getUniqueIndexes` loads every unique index (`Non_unique=0`), parts in `Seq_in_index` order. `buildColumnMapping` (`model.go`) walks the source columns in source order, applies `CHANGE COLUMN` renames from `parseChangeColumnRegex`, and keeps each pair whose destination exists on the temp table and is not generated. A generated source column whose destination exists and is stored is an error: triggers cannot read generated columns. Source generated with a generated destination, or a missing destination, is skipped. That one list is the copy's insert list and select list, and the column list the three triggers write, so an `AFTER` or `FIRST` reorder can't mis-pair them. Unique coverage also counts a derived column: a generated column whose expression is a conditional projection (`` `col` ``, or `if(<cond>, `col`, NULL)` / `if(<cond>, NULL, `col`)`) of a copied column, with the generated type equal to the projected column's type on each side, and a condition that is one integer column compared with an integer literal, unchanged by the alter. Any other generated column in a destination unique index has to be covered without that proof. `checkUniqueCoverage` requires, for every destination unique index, a source unique index whose every part maps to one of the destination's parts, so extra destination parts need no proof. Copied columns and derived columns both count. A functional source index covers nothing. Parts compare on column name and prefix length exactly. A collation change on a destination unique column that is copied or derived is refused. `keyConversionKeepsValues` refuses a conversion that does not keep values on a mapped unique column, for every unique index, the primary key included, because two distinct source rows could land on one destination key. `destinationKey` requires a destination primary key. It is that key in destination key order, each column paired with the source column copied into it. A destination key column that is not a mapping destination is an error. The storage engine of the source and temp tables must match. Inbound foreign keys (other tables that reference this one) re-attach by name after the rename, so every referenced column must map to a destination column with the same name, identical `COLUMN_TYPE`, and identical character set and collation, and the destination must have an index whose leading parts are exactly those columns in that order with no prefix length. After `destinationKey`, and before any mirror trigger exists, `readRestorePlan` builds one restore plan and `validate` compiles it against a probe table (`<table><suffix>probe_`) created `LIKE` the temp table. The probe proves the foreign key definitions and the original trigger bodies compile against the altered columns. It does not prove the rename, permissions, or anything another session changes. Either check failing stops the run before any trigger is created and before the run record is written. The temp table is left, and the next run drops it.
3. **Install three triggers** on the source table (`*_after_delete_smgla_`, then `*_after_update_smgla_`, then `*_after_insert_smgla_`) that mirror writes into the one temp table. They are created on the pinned connection after `set session sql_mode=@@global.sql_mode`, because a trigger keeps the sql_mode it was created with and the application's sessions use the server's global mode. None of them uses `IGNORE`. The delete trigger deletes the temp row whose destination key equals the old source key. The update trigger updates that temp row in place (so a primary-key change moves it and destination-only columns stay), then inserts the new row only when no temp row has the new key. The insert trigger inserts the new row. A write the destination rejects fails the application's statement. A resumed run does not create them. After the same `sql_mode` set, it loads the run record and refuses, with `; rerun with -fresh to start over`, on the first mismatch: no run row (a temp table from a run that never wrote one cannot be resumed), the run table is not InnoDB, the alter text differs, the normalized source or temp create statement differs, the `k0…` columns are not the traversal key, or a mirror trigger is missing, is not the after delete/update/insert trigger on the source, has a different body, or has a different `sql_mode`. Matching bodies are what proves these triggers have been mirroring since the first chunk.
4. **Bulk-copy rows in primary-key chunks, inside the server, on that same connection.** Before each chunk, pacing reads `information_schema.replica_host_status` (the writer's row is `SESSION_ID = 'MASTER_SESSION_ID'`). A reader is behind when its reported `REPLICA_LAG_IN_MILLISECONDS` is over `-max-lag`, or when its `LAST_UPDATE_TIMESTAMP` is more than 10s old. A healthy reader's status row is refreshed about once a second, so that age is not lag. The copy logs a stale row as the reader stopped reporting. A reader this run has already seen and that then disappears also pauses the copy. The copy waits, logging once and then every 60s, until every known reader is present, reporting, and within `-max-lag` (default 1s; `0` turns pacing off). No flag is needed to pace. Error 1109 means the server is not Aurora, and pacing turns off. A status-read error stops the run; the triggers keep mirroring, and the next run continues. The known readers are stored in the run table and seeded again on resume. `-forget-readers` clears that list on a resumed run. With no stopped run to resume, it logs that it has no effect and the run continues. Pauses are not part of the chunk time. If `copy_done` is already 1, the copy loop is skipped. Otherwise a saved non-null `k0` is loaded into `@smgla_k*` and the copy continues after that key. The progress bar's total stays the source row count and starts at 0. Each chunk is `start transaction`, the copy, the warning check, then either `update` of `k0…` from `@smgla_e*` or `copy_done=1`, then `commit`. The end-key query stays outside the transaction. A warning fatal exits the process; the connection drops and InnoDB rolls the chunk back, so a resumed run never keeps a warned chunk. `lock in share mode` holds the copied range until that commit. The copy statement is `insert into <temp> (...) select ... from <source> where <range> lock in share mode on duplicate key update <first column>=<first column>`. A duplicate is the row a trigger already wrote, which unique coverage makes the only kind, and the no-op keeps it without a warning. The range is lexicographic on the source traversal key (the full source primary key in index order), compared against session variables `@smgla_k*` (the cursor) and `@smgla_e*` (this chunk's end key). The end key is the chunk-th key after the cursor: `order by <pk> limit 1 offset chunk-1`. Key values are never read into Go.
5. **Adaptive chunk sizing.** Each copy statement is timed against a 500ms target. Over target, the chunk shrinks proportionally (`chunk * target / elapsed`, minimum 1). Under target, it grows by a tenth of the gap, and it does not grow past 10000 rows. Any warning from a copy statement stops the tool (`failOnCopyWarnings`, `copywarnings.go`). That rule is stricter than the triggers because the copy governs rows that already exist: a row that breaks a check constraint, or a value the alter narrows, must not be skipped or changed without an error. `-r` is the starting chunk size (default 1000, 1 to 10000).
6. **Swap / restore, still on that connection.** After a `do the drop/swap?` y/n confirmation the plan is read again (fresh `SHOW CREATE TABLE` → `splitConstraints`, fresh trigger read, fresh inbound keys). If it is not `equal` to the validated plan, the run stops before the swap: the source's triggers or foreign keys changed during the copy; rerun the tool. That re-check is a cheap guard for the assumption that no other DDL ran on the table or its foreign key neighbors, not a proof. Answering `n` exits 0 and leaves the temp table, the mirror triggers, and the run record in place. The next run continues it. `chooseCutOver` then picks the strategy from that plan and one `select version()`, and the choice is logged once.

`cutOverAtomic` applies when the plan has no foreign keys of its own and no inbound foreign keys, and the leading `major.minor.patch` of the version is MySQL 8.0.13 or newer (`RENAME TABLE` of a write-locked table needs 8.0.13; Aurora MySQL 3 reports `8.0.x-...`). Anything unparsable or older is `cutOverDropFirst`. The log line is `swapping under lock tables: the table has no foreign keys`, or `swapping by drop then rename:` with the reason (the table has foreign keys, or the server is older than 8.0.13). Foreign keys follow a renamed table, and a foreign key name is unique in the schema, so it cannot sit on both the old table and the new one. With no foreign keys, that reason is gone: the swap holds `LOCK TABLES`, other sessions wait on the lock, and they see the new table when it is released. With any foreign key, the original table is dropped before the rename, and between those two statements the name does not exist (error 1146).

Before anything is created, fresh or resumed, `<table><suffix>old_` is checked against 64 characters, same as the run table. If that table already exists, the tool refuses and does not drop it. The recovery file `smgla-recovery-<table>-<unix seconds>.sql` is written before the drop or the lock. A write failure stops with nothing swapped. Both files start with `use <database>;` and `set names <charset>;` from `@@character_set_client`, because `SHOW CREATE TRIGGER` comes back in that character set. `retargetTrigger` (`triggers.go`) rewrites the trigger name and the table in the `TRIGGER … ON … FOR EACH ROW` header. The swap statements run without a transaction.

`cutOverDropFirst` writes the plan's `steps` (the combined foreign-key `ALTER TABLE`, each original trigger's `sql_mode`/`collation_connection` then `CREATE`, the session restore, then `ALTER TABLE … RENAME`) and runs them after `set foreign_key_checks=0` and the drop. Each success logs `done: <Purpose>`. A failing step names the step, MySQL's error, that `<table>` is dropped and its rows are in `<temp>`, and that the remaining steps in the recovery file finish the swap. After the rename succeeds, the run table is dropped. It is not part of the recovery file. If that drop fails, the error is logged with the table name and the process exits 0: the swap is already done.

`cutOverAtomic` writes the undo instead, with no `foreign_key_checks` line: for every original trigger, `drop trigger if exists` (the name may already sit on the temp table) and the original `CREATE TRIGGER` on the source under its own `sql_mode` and `collation_connection`, then the session restore. The locked sequence, all on the pinned connection, is:

1. **Lock.** When `@@session.lock_wait_timeout` is higher than 10 it is set to 10, then `LOCK TABLES <table> WRITE, <temp> WRITE, <run> WRITE`. The run table is in the lock so it can be dropped before the unlock. MySQL also locks every table the locked tables' triggers use. A failure here changes nothing. The temp table, mirror triggers, and run record stay, and a rerun resumes at the swap prompt. The saved `lock_wait_timeout` is put back after the unlock.
2. **Move the originals.** Each original trigger is dropped from the source, in plan order, then each is created on the temp table under its own `sql_mode` and `collation_connection`. Trigger names are unique in the schema, so every original leaves the source before any is created on the temp table. The mirror triggers stay on the source. The lock blocks writes, and the mirrors leave with the old table.
3. **Swap.** The session `sql_mode` and `collation_connection` are restored, then `RENAME TABLE <table> TO <old>, <temp> TO <table>`, then the run table is dropped. The run record must not outlive the rename: a crash after it would leave a record whose source and temp schemas no longer exist.
4. **Unlock.** `UNLOCK TABLES`, and `lock_wait_timeout` goes back. A failure here is logged and the process exits 0.
5. **Clean up.** `<old>` is dropped. A failure here is logged with the table name and the process exits 0. The swap is already done. A failure after the rename has succeeded is not undone.

If a statement fails before the rename succeeds, the lock is still held, so the tool undoes and only then unlocks: it drops every original trigger already created on the temp table, re-creates every original trigger already dropped from the source from the `SHOW CREATE TRIGGER` statement stored before retargeting, restores the session values, unlocks, and exits 1. The mirror triggers never moved and writes were blocked, so the temp table is still exact and a rerun resumes at the prompt. If an undo statement fails, or the connection is gone (the server releases the locks when the session ends), the tool stops and names the recovery file. The same rerun resumes at the prompt.

### Primary key

`destinationKey` pairs each destination primary-key column, in destination `Seq_in_index` order, with the source column the mapping copies into it. The delete trigger matches the old source key. The update trigger matches the old source key, writes the new values in place, and inserts when the new key is absent. Unique coverage is what makes that key identify one source row, including when the primary key grows, shrinks, or is renamed.

## Code map

- `main.go` — full orchestration (steps above). Most logic still lives here; resist the urge to split it just for tidiness.
- `pacing.go` — Aurora reader lag, and the pacer that waits before each chunk.
- `run.go` — the run table, the checkpoint SQL, `normalizeCreate`, and the resume decision.
- `columns.go` — `information_schema` queries; primary-key detection, `Seq_in_index`, `COLLATION_NAME`, `CHARACTER_SET_NAME`, and indexes from `SHOW INDEX`. Also handles older MySQL versions that lack `GENERATION_EXPRESSION` (probes `information_schema` for the column itself before selecting it).
- `model.go` — the column mapping, unique-index coverage, the destination key and which key conversions keep values, the source traversal key, and the check that every traversal-key type can live in a user variable.
- `keyrange.go` — identifier quoting (`quoteIdent`, `quoteString`) and lexicographic `after` and `atOrBefore` predicates over the session-variable cursor.
- `constraints.go` — splits foreign keys out of `SHOW CREATE TABLE` by the token after the constraint name, gives generated check constraints temp names, and rewrites those names in the user's alter outside literals and comments. `referentialActionSkipsTriggers` is the cascading-action rule.
- `restore.go` — the restore plan, the locked and drop-first swaps, probe validation, recovery SQL, inbound foreign keys, and the post-drop step helper.
- `regexp.go` — two regexes: parse the user's alter into `(schema, table, alter-body)`, and find `CHANGE COLUMN` renames.
- `triggers.go` — rewrites the trigger name and table in the `TRIGGER … ON … FOR EACH ROW` header of `CREATE TRIGGER`, and reads `SHOW CREATE TRIGGER` for the statement text.
- `prompt.go` — `nano`-based alter input, `Y/n` confirmation reader.
- `connections.go` — YAML config loader and DSN builder (uses `go-sql-driver/mysql`'s `NewConfig` then appends URL-escaped extra params).

## Conventions

- Error handling is `panic`-on-error for setup failures in `main.go`. This is intentional: every setup panic happens before any mirror trigger exists, so the next run starts clean, and a panic is the clearest signal. Don't convert these to silent error returns. Refusals and the mirror session use `log.Fatalf`: the traversal-key type check, cascading and self-referential foreign keys, unique coverage, the destination key, inbound keys, the column mapping, probe validation, a resume mismatch, a replica-lag read error, and every statement on the connection from the lookups through the swap. The message names what failed. A lag-read error leaves the triggers mirroring so the next run can continue. After the drop, a failing restore step also names the recovery file. A locked swap that cannot undo names it too.
- SQL identifiers go through `quoteIdent` (backticks, doubled internally). String literals in restore SQL go through `quoteString`. Table names come from the user's alter statement (parsed by regex), not from arbitrary input — but be careful adding new code paths that would interpolate untrusted strings into DDL.
- One `database/sql` connection (`db.Reads.Conn`; `db.Writes` has no `Conn`, and both pools use the same DSN) is pinned after the source columns are read and held through the swap, with `?` placeholders for lookups that bind table names as values. It does not go through cool-mysql interpolation, so `sql_mode`, `foreign_key_checks`, the copy's isolation level, and the `@smgla_*` cursor stay on that session. Statements before that connection still go through cool-mysql. Its placeholders are `@@name` (compile-time interpolated, often as `mysql.Raw`) and `@name` (parameter-bound).
